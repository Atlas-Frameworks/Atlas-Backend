# OpenShift deployment (task I-04)

Helm charts for everything the team maintains. Plan: `docs/architecture-plan.md`, sections
"Multi-pod deployment without sticky sessions", "Deploys and scaling" and "Write path" item 6;
caveats 31 and 42. Contracts: `docs/contracts.md` §2, §4, §8.

| Path | What |
| --- | --- |
| `charts/view-service/` | One view service: StatefulSet, headless Service (gRPC), Service + Route (WebSockets), HPA, PodDisruptionBudget |
| `charts/view-service/values-tracks.yaml` | Service `tracks` (airplanes) |
| `charts/view-service/values-reference.yaml` | Service `reference` (airports, countries) |
| `charts/atlas-pipeline/` | Debezium Server (Deployment + ConfigMap + Service) and replicator-sim (Deployment + Service), installed once |
| `schemas/route.openshift.io/route_v1.json` | OpenShift Route JSON schema for kubeconform (generated) |
| `scripts/validate.sh` | Lint, render every values combination, validate with kubeconform (also run in CI) |
| `scripts/update-route-schema.sh` | Regenerates the Route schema from `openshift/api` |

## Why Helm, not Kustomize

- **Two services from one chart** (S-10) is Helm's normal model: `helm install tracks` and
  `helm install reference` with different values files. With Kustomize this is two overlays that
  patch names, labels, selectors, env and Route hosts separately, and a forgotten patch silently
  merges two worker lists.
- **Derived values.** Several settings are computed from others: the headless Service name inside
  `WORKER_ADDRESS`, `ENTITY_TYPES` from a list, the Debezium JDBC URL from the database host,
  dropping the separate WebSocket port when it equals the HTTP port, the optional custom HPA
  metric, and a config checksum that restarts Debezium when its properties change.
- `helm template` renders offline, so CI validates without a cluster; OpenShift's console and
  `oc` support Helm releases directly.

## Install

```bash
oc new-project atlas
# Secrets are created outside the charts (no passwords in values files).
oc create secret generic atlas-view-service-db \
  --from-literal=PG_PRIMARY_URL=postgres://... --from-literal=PG_REPLICA_URL=postgres://...
oc create secret generic atlas-debezium-db --from-literal=password=...

helm upgrade --install atlas deploy/charts/atlas-pipeline
helm upgrade --install tracks deploy/charts/view-service -f deploy/charts/view-service/values-tracks.yaml
helm upgrade --install reference deploy/charts/view-service -f deploy/charts/view-service/values-reference.yaml
```

Image names, tags, ports, probe paths, addresses and secret names are all values.

## Validate

```bash
npm run deploy:validate        # = bash deploy/scripts/validate.sh
```

It uses pinned Docker images (`alpine/helm:3.22.0`, `ghcr.io/yannh/kubeconform:v0.8.0`); set
`HELM=helm KUBECONFORM=kubeconform` to use local binaries. It runs `helm lint --strict` on both
charts, renders five cases into `deploy/.rendered/` (tracks, reference, tracks with the custom HPA
metric, tracks with the HPA off and a shared HTTP/WS port, the pipeline), and validates them with
`kubeconform -strict` against Kubernetes 1.33 schemas (OpenShift 4.20 ships Kubernetes 1.33).

The Route is not in kubeconform's default schemas, and the datreeio CRDs-catalog has no Route
(it is an OpenShift API, not a CRD on most clusters). `schemas/route.openshift.io/route_v1.json`
is generated by `scripts/update-route-schema.sh` from the Route CRD in `openshift/api`
(`release-4.20`, `route/v1/zz_generated.crd-manifests/routes.crd.yaml`), converted the same way as
kubeconform's `openapi2jsonschema.py` in strict mode, so unknown fields and bad enum values fail.

## view-service

- **StatefulSet** so pod names, which are the worker names and the hashing input, survive
  rollouts (caveat 42). `WORKER_NAME` comes from `metadata.name` through the downward API.
- **`podManagementPolicy: Parallel`** only changes scale up and down. `RollingUpdate` still
  replaces one pod at a time (highest ordinal first) and waits for it to be ready, plus
  `minReadySeconds` (15 s: the 10 s membership anti-flap window plus margin). This is the
  StatefulSet form of `maxUnavailable: 0, maxSurge: 1` from the plan. The beta
  `rollingUpdate.maxUnavailable` field is deliberately not set.
- **Probes:** startup and liveness on `/health/live`, readiness on `/health/ready` (registered in
  membership and caught up with the streams), all on the named `http` port.
- **Shutdown:** `preStop` sleeps 5 s so the router and endpoints stop sending new connections, then
  SIGTERM starts the S-07 sequence (not ready, leave membership, make-before-break handover up to
  20 s, `Reconnect` with 0–15 s jitter, exit). `terminationGracePeriodSeconds: 60` covers it.
- **Memory:** `NODE_OPTIONS="--max-old-space-size=2560 --max-semi-space-size=32"`; requests =
  limits = 1 CPU / 4 GiB (Guaranteed QoS).
- **Headless Service `<svc>-view-peers`** for gRPC (contracts §4). Each worker is reachable at
  `<pod>.<svc>-view-peers.<namespace>.svc.cluster.local`, passed as `WORKER_ADDRESS` for the
  membership entry. `publishNotReadyAddresses: true`, because an owner that is shutting down is
  not ready but must keep streaming to subscribers during the handover.
- **Service + Route** for WebSockets, edge TLS (`insecureEdgeTerminationPolicy: Redirect`), with
  `haproxy.router.openshift.io/disable_cookies: "true"`, `.../balance: leastconn`,
  `.../timeout: 60s` (caveat 31). Annotation names and values were checked against the
  **OpenShift Container Platform 4.20** docs (Ingress and load balancing > Routes >
  Route-specific annotations): `disable_cookies` accepts `true`/`TRUE`; `balance` accepts
  `random`, `source`, `roundrobin`, `leastconn` (default `random`); `timeout` takes a number plus
  unit (`us`, `ms`, `s`, `m`, `h`, `d`). Caveat 31 asks for a timeout above 60 s; the client pings
  every 16 s, so 60 s is ample, and it is a value. If upgraded WebSocket connections turn out to
  use HAProxy's tunnel timeout instead, add `haproxy.router.openshift.io/timeout-tunnel` through
  `route.extraAnnotations` (not verified on a cluster).
- **HPA** min 3, max 5, on memory at 70% of the request (the plan's scale-out trigger), adding or
  removing one pod at a time (each change moves about 1/N of the views). On first install the
  chart sets `replicas: minReplicas`; on upgrades it leaves the count to the HPA.
  - **Optional custom metric** (`autoscaling.customMetric.enabled`, off by default): a `Pods`
    metric, default `atlas_entities_held` (contracts §8) with an average target per pod. It needs a
    custom metrics API on the cluster, for example prometheus-adapter or KEDA reading OpenShift
    user-workload monitoring, and a ServiceMonitor scraping `/metrics` (task I-05).
- **PodDisruptionBudget** `maxUnavailable: 1`, so node drains also go one worker at a time.
- Pods run under the `restricted-v2` SCC (non-root, no privilege escalation, all capabilities
  dropped, RuntimeDefault seccomp, no UID pinned) and spread across nodes by preferred
  anti-affinity.

## Debezium

- **One replica, `strategy: Recreate`**: a replication slot serves one reader, so the old pod stops
  before the new one starts (plan, "Write path" item 6). `terminationGracePeriodSeconds: 120` lets
  it flush offsets and release the slot.
- **Config** in a ConfigMap mounted at `/debezium/config/application.properties`. It mirrors
  `infra/debezium/application.properties` (owned by I-03; keep them in sync), with
  `debezium.database.host` = the **Patroni primary Service** (value, default `atlas-postgres`) and
  `debezium.redis.address` = the master-only Redis proxy (value, default `redis-proxy:6380`). The
  password comes from a Secret as `ATLAS_DB_PASSWORD` and is referenced as `${ATLAS_DB_PASSWORD}`.
  A checksum annotation restarts the pod when the properties change.
- **Image:** must be built from `infra/debezium/Dockerfile` (being added by I-03):
  `quay.io/debezium/server:3.7.0.Final` plus
  `/debezium/lib_opt/debezium-connect-plugins-3.7.0.Final.jar` copied into `/debezium/lib/`,
  because the Outbox `EventRouter` is not on the stock image's classpath. The stock image fails
  to start the transform. Set `debezium.image.repository`/`tag` to wherever that image is pushed.
- **Liveness is required, not decoration:** when the Redis master is demoted, Debezium Server 3.7's
  Redis sink fails its engine (`JedisDataException "UNBLOCKED force unblock..."`) but the JVM
  keeps running, so it never restarts on its own. `GET /q/health/live` (port 8080) reports DOWN
  in that state, and the liveness probe (every 10 s, 3 failures) restarts it. A startup probe
  allows up to 120 s before liveness starts, so a slow start isn't killed. Readiness is
  `GET /q/health/ready`.
